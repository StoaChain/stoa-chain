# pact/stoa-coin/upgrades

Reference-only snapshots of the live, post-genesis `coin` module.

## These files are NOT executed by the node

StoaChain nodes boot from the genesis payloads compiled into the binary:

- `src/Chainweb/BlockHeader/Genesis/Stoa0Payload.hs`
- `src/Chainweb/BlockHeader/Genesis/Stoa1to9Payload.hs`

Those payloads are generated by `cwtools/ea` from the source under
`pact/stoa-coin/new-coin.pact` and the YAMLs under `pact/genesis/stoa/`.

**Those genesis inputs are frozen forever after the first block is mined.**
Changing any of them and regenerating the payloads would produce a different
block-0 hash — any binary built from the changed source would compute a
block-0 that disagrees with the live network and would not be able to sync.

## How on-chain upgrades work

After genesis, the `coin` module can be upgraded on-chain via a governance
transaction signed by the 7 Stoa Masters keysets (1-of-7 via `enforce-one`).
The upgrade transaction becomes permanent chain history. Any node syncing
from block 0 replays the full transaction history in order, so it arrives
at the current (upgraded) module state automatically — no code change,
recompile, or restart required.

## What lives in this folder

Read-only textual snapshots of what the live `coin` module looks like at
a given point in time. They are useful for:

- Code review of what is currently executing on-chain.
- Audit trails — diffing successive snapshots shows what each governance
  upgrade changed.
- A starting point for drafting the next governance upgrade transaction.

If you need the live module programmatically, the authoritative source is
the chain itself — fetch it with `describe-module` against a running node
(e.g. `node1.stoachain.com` / `node2.stoachain.com`).

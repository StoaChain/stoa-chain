# HANDOFF — AncientStoa branch

> Read this first if you're a fresh context picking up work on this branch.
> This is a living document. Update it when the branch's purpose changes.

## Why this branch exists

`AncientStoa` is a **safe-to-experiment branch**. The `main` branch is what
`node1.stoachain.com` is running against in production (the live StoaChain
network). We cut `AncientStoa` so we can iterate on containerisation, hub
integration, and other ops tooling without risking the live network.

**Nothing merged to `AncientStoa` goes to production automatically.** The live
server pulls `main`. When work here is stable, we'll review and cherry-pick
the ops bits into `main`.

## What StoaChain is (one-paragraph primer)

StoaChain is a **software fork** of Kadena's `chainweb-node` (Haskell, braided
parallel-chain Proof-of-Work). It is NOT a chain fork — it's an independent
network with its own genesis, its own coin contract, its own bootstrap peers.
Kadena mainnet and StoaChain share no ledger state. The fork adds a new
`ChainwebVersion` called `stoa` to the upstream version registry; everything
Stoa-specific is gated behind that identifier.

Read [CLAUDE.md](CLAUDE.md) for the architecture details and the version-wiring
spine (the seven-step list that must stay in sync when touching consensus
inputs).

## Immutable constraints — DO NOT VIOLATE

These rules come from how Chainweb bootstraps itself. Violating them produces
a chain that cannot sync with the live network.

### Genesis inputs are frozen forever

Every node computes block 0 **locally** from data compiled into its binary
(`src/Chainweb/BlockHeader/Genesis/Stoa0Payload.hs`, `Stoa1to9Payload.hs`).
Those Haskell modules are generated by `cwtools/ea` from:

- `pact/stoa-coin/new-coin.pact`
- `pact/genesis/stoa/*.yaml` and their referenced `.pact` files

**Changing any of those files and rebuilding produces a different block-0
hash.** A node built from the changed source will reject the live network's
block 0 and refuse to sync. Do not modify these files on this branch (or on
`main`) under any circumstance.

For the same reason, `_versionGenesisTime`, `_versionGenesis`, the chain
graph, block delay, fork heights, and verifier plugin set in
[src/Chainweb/Version/Stoa.hs](src/Chainweb/Version/Stoa.hs) are also frozen.

### On-chain upgrades are separate

The live coin module has been upgraded on-chain since genesis via a governance
transaction (1-of-7 Stoa Masters `enforce-one`). That upgrade is part of the
chain's transaction history and is replayed automatically by any syncing node
— no code change needed on our side.

A read-only snapshot of the live coin module is kept at
[pact/stoa-coin/upgrades/live-coin-module.pact](pact/stoa-coin/upgrades/live-coin-module.pact)
for audit/review. **That file is not executed by the node.** See
[pact/stoa-coin/upgrades/README.md](pact/stoa-coin/upgrades/README.md).

### Safe to modify freely

Anything not in the consensus set above: `README.md`, `HANDOFF.md`, this file,
`CLAUDE.md`, `CHANGELOG.md`, `deploy.sh`, `run-stoa.sh`, `stoa-node.service`,
`Dockerfile`, `docker/`, `assets/`, comments, formatting. The bootstrap peer
list in `Stoa.hs` is also safe — it affects network discovery, not consensus.

## The Docker work (current focus)

### Goal

The live node currently runs as a bare-metal `cabal`-built binary managed by
systemd ([stoa-node.service](stoa-node.service), [run-stoa.sh](run-stoa.sh)).
We want a containerised variant so that a separate orchestrator — the **Stoa
Hub** — can start, stop, and reconfigure nodes across multiple servers
without manual SSH, build, and service-file editing.

### What's added on this branch

- **`Dockerfile`** — The repo already had an upstream Kadena Dockerfile with
  multi-stage build caching. We added a new final stage `stoa-node` that
  extends the `chainweb-node` stage (fast — no test run) with a hub-friendly
  entrypoint. Because it's the last stage, plain `docker build .` targets it
  by default. The tested image is still available via
  `docker build --target chainweb-node-tested .`

- **`docker/entrypoint.sh`** — Wrapper script that translates environment
  variables into `chainweb-node` CLI flags. The full env-var surface is
  documented in the header comment of that file. Key contract:
  - Required env var: `P2P_HOSTNAME` (public hostname the node advertises).
  - Conditional: `MINING_PUBKEY` when `ENABLE_MINING=true`.
  - All other flags have sensible defaults or an `EXTRA_FLAGS` escape hatch.
  - Positional args after the image name on `docker run` are forwarded too.

- **`.dockerignore`** — Keeps the build context small (excludes
  `dist-newstyle`, `.git`, local RocksDB dirs, editor cruft).

### How to build and run

```bash
# Build the hub-ready image (defaults to the stoa-node stage).
docker build -t stoa-node:latest .

# Run it.
docker run -d --name stoa-node \
  -p 1789:1789 -p 1848:1848 \
  -v stoa-data:/data \
  -e P2P_HOSTNAME=node1.stoachain.com \
  stoa-node:latest

# With mining:
docker run -d --name stoa-node \
  -p 1789:1789 -p 1848:1848 \
  -v stoa-data:/data \
  -e P2P_HOSTNAME=node1.stoachain.com \
  -e ENABLE_MINING=true \
  -e MINING_PUBKEY=<hex> \
  stoa-node:latest
```

Build expects ~10 GB RAM and ~30 min on first build; subsequent builds hit
the cabal/dist-newstyle buildx cache.

### What's intentionally NOT yet decided

The user explicitly deferred these decisions so that the Hub conversation
(a different Claude Code context, with the hub's requirements in view) can
own them:

1. **How the Hub passes flags.** The entrypoint supports env vars, positional
   args, and `EXTRA_FLAGS` passthrough, so all three patterns work:
   - `docker run -e ENABLE_MINING=true ...` (env vars) — simplest
   - `docker run <image> --log-level debug` (positional) — ad hoc overrides
   - Mounted config file + `EXTRA_FLAGS=@/path/to/config` (if you extend the
     entrypoint) — structured config
   The Hub conversation should pick whichever fits its orchestration model.

2. **Where the image is built.** User has a server with 32 GB RAM and SSH
   access; they prefer to build there for now instead of setting up GitHub
   Actions + GHCR. That works. If they later want shared images across
   multiple servers, add a `.github/workflows/docker.yml` that builds and
   pushes to `ghcr.io/stoachain/stoa-node:<tag>`.

3. **Image registry.** Not set up. Current plan: build on server, image stays
   on server. Add GHCR later if multi-server deployment happens.

4. **Database persistence / backup story.** Currently `/data` is a Docker
   volume. Host bind-mount (`-v /var/lib/stoa:/data`) may be preferred for
   backup/inspection — that's an ops call.

5. **Network mode.** Example above uses bridge + explicit port mapping. Host
   mode (`--network host`) is simpler for P2P and may be preferred for a
   single-node-per-machine setup. Operator's call.

## For the Hub conversation

If you're the AI picking up hub integration:

1. **Read this file first**, then [CLAUDE.md](CLAUDE.md), then skim
   [run-stoa.sh](run-stoa.sh) to see the flags the production node currently
   uses.
2. The hub's interaction point with this repo is the container. Your
   decisions live in the hub codebase, not here. You probably don't need to
   modify anything on this branch — but if the env-var surface is missing
   something you need, extend `docker/entrypoint.sh` and document it in its
   header comment.
3. The user has the server's SSH key in your context. You can SSH in to
   build and run the container directly. The user prefers that over setting
   up CI/registry right now.
4. **Do not** modify files listed under "Immutable constraints". If you're
   not sure whether a change is safe, ask.
